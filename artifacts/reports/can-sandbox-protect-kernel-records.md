# Report: Can a sandbox protect kernel records

## Summary
On Linux and WSL2 the Bash sandbox can deny writes to chosen paths (`sandbox.filesystem.denyWrite`) while command hooks, which run outside it, keep writing them [VERIFIED]. On native Windows there is no sandbox, so this route does not exist there [VERIFIED]. The documents show one sandbox configuration per session and no per-subagent or per-tool scope, so the lead's Bash and an agent's Bash most likely get the same rules; the only documented difference is that hooks carry `agent_id` and `agent_type`, which the sandbox does not [INFERRED]. Most record writers today are `picket` verbs run from Bash, so a read-only record path stops the lead's verbs too, unless they are excluded commands, and an excluded command runs with no restriction at all [INFERRED]. Hiding PICKET_DATA_<SERVICE> from agents is possible with `credentials.envVars` deny, but `picket data run` reads that variable in a Bash-run verb and needs the container engine, which fails in the sandbox, so that verb has to run outside it [INFERRED].

## Context
Scope as understood: decide whether the host's OS-level sandbox can make the kernel's record paths read-only for agents' shells while hooks and the lead's `picket` verbs still write them (SDR 00005 TF-003), on Linux, WSL2 and Windows, and name what would have to move into hook processes and what cannot be done. No design is proposed. Not read: the end of the sandbox page (Security limitations), the `sandbox` defaults in the settings reference, the `PreToolUse` decision section and `CLAUDE_ENV_FILE` text of the hooks page, the agent teams page, and the full permissions page, because the fetch tool returned truncated text. Nothing was run; no sandbox was probed.

## Structure
Records are named by two code paths. `KERNEL_OWNED_ENTRIES` lists the per-item kernel files (state.yaml, verdicts.jsonl, comments.jsonl, waivers.jsonl, mutation.json, left.jsonl, phases/, request.md, story.md, sources.yaml, sources/, repos.yaml, test/, test.md), and `isHookOnlyState` marks every file under `.picket/state/` except `scratch/`, `branching.yaml` and PR ticket files. `guard.bash` denies a shell command that names one of these paths; it reads command text, not what a script does. Hooks are small processes started by `runHook`, which reads the event from stdin, runs one handler, writes JSON to stdout and appends the ledger.

## Findings
- **R-001** [VERIFIED] The sandbox wraps only shell commands (Bash, PowerShell, Monitor) and their children. Command hooks, local MCP servers, the status line command and plugin monitors run with full access. `https://code.claude.com/docs/en/sandboxing`, "Hooks and other processes".
- **R-002** [VERIFIED] Filesystem rules are `allowWrite`, `denyWrite`, `denyRead`, `allowRead`; arrays merge across settings scopes; for read rules the narrower path wins. Keys exist for `sandbox.filesystem.denyWrite` in any settings file. `sandboxing`, "Filesystem rules"; `settings-reference`, sandbox key table.
- **R-003** [VERIFIED] Linux and WSL2 use bubblewrap and socat; WSL1 is unsupported; native Windows runs commands unsandboxed, and unless `failIfUnavailable` is true the session continues. `sandboxing`, "Platform support". Windows has no OS isolation route.
- **R-004** [INFERRED] The documents describe one sandbox per session and never scope it to a subagent or tool. The sub-agents page says a subagent's tool call "still goes through the session's permission checks and sandboxing", and subagents inherit the parent's permission rules and mode; only an `isolation: worktree` subagent differs, by running its Bash inside its worktree. The agent teams page and the sandbox page's end were not read. `sub-agents` (excerpt); `sandboxing`. [ARCHITECT REVIEW NEEDED]
- **R-005** [VERIFIED] `credentials.envVars` entries with `"mode": "deny"` unset the variable before each sandboxed command, and this protection stays when filesystem isolation is off; `mask` swaps in a placeholder and needs the network proxy. Unsandboxed commands (excluded, the `!` prompt, hooks) keep the variable. `sandboxing`, "Environment variables" and credentials example.
- **R-006** [VERIFIED] `excludedCommands` run with no filesystem restriction and no proxy. Matching is on call text: every command in a chain must match, a script that calls the program inside does not match, and calls with a redirect, `cd` or `$(...)` stay sandboxed. A broad entry lets Claude write a file and run it outside. `sandboxing`, "excludedCommands".
- **R-007** [VERIFIED] A failed sandboxed command can be retried with `dangerouslyDisableSandbox`; approval depends on mode (none in bypassPermissions, classifier in auto, denied in dontAsk). `allowUnsandboxedCommands: false` removes the retry, and a false in user, managed or `--settings` beats project settings; managed settings with it false make the sandbox admin-required and ignore repository `excludedCommands` and `allowWrite`. `sandboxing`, "dangerouslyDisableSandbox", "Managed settings".
- **R-008** [VERIFIED] The sandbox always denies writes to Claude's own config (`.claude` settings, skills, agents, commands, hooks, `.mcp.json`, `.git/hooks` and `.git/config`). Only `filesystem.disabled` lifts this, and project settings cannot set it. `sandboxing`, "Protected paths". This repository's `.claude/settings.json` and `.claude/agents` are already covered, `.picket/` and `work/` are not.
- **R-009** [VERIFIED] `docker` is incompatible with the sandbox; rootless Podman and Buildah fail inside it, and the documented fix is an `excludedCommands` entry that runs them with full access. On Linux and WSL2 sandboxed `localhost` is private to the command, and most database drivers ignore the proxy variables. `sandboxing`, "Docker and Podman", "Network", troubleshooting headings 5, 16, 17.
- **R-010** [VERIFIED] Sandbox rules cover shell commands only; built-in Write and Edit follow permission rules instead. `sandboxing`, "Hooks and other processes". A record path would need both a sandbox `denyWrite` and an `Edit(...)`/`Write(...)` deny rule; the permissions page was read only in part.
- **R-011** [VERIFIED] This repository's committed settings carry no `sandbox` block. Allow rules include `Bash(picket *)`; `picket drive` and `picket check` are `ask` only under PowerShell. `.claude/settings.json`.
- **R-012** [VERIFIED] SDR 00005 D-005, D-006 and RISK-003 state the open question: every record write would move into hook processes, and the sandbox must keep chosen paths read-only while hooks write them. `artifacts/strategy/decisions/00005-irreversible-actions-are-confirmed-point.md`.
- **R-013** [INFERRED] The lead and the user's verbs run from Bash like an agent's. If record paths are read-only there, every record-writing verb fails unless it is an excluded command; an exclusion for `picket *` would also run any command beginning with `picket` unsandboxed, and call-text matching (R-006) is the same kind of text reader that `guard.bash` already is. [ARCHITECT REVIEW NEEDED]
- **R-014** [VERIFIED] Hooks from settings, managed policy and plugins also run inside subagents, and tool events carry `agent_id` and `agent_type`; hooks run in the current directory with Claude Code's environment. `https://code.claude.com/docs/en/hooks`, "Hooks inside subagents". `runHook` already uses `event.agent_type` to name the agent in the ledger, defaulting to "lead". `src/lib/hooks/run-hook.mts:42-47`. A hook, unlike the sandbox, can tell the lead from an agent.
- **R-015** [VERIFIED] A timed-out `PreToolUse` command hook does not block the tool call, except for hooks whose failure blocks the action; `runHook` returns null (allow) when a handler throws. `hooks`, "Timeouts"; `src/lib/hooks/run-hook.mts:27-33`. A control that rests on a hook is fail-open on crash or timeout.
- **R-016** [VERIFIED] `picket data run` writes records from the Bash-run verb: it appends a `taken` row to the confirmations file, appends a data run row, and reads the connection string from its own environment (`PICKET_DATA_<SERVICE>`), then starts the container engine with `-e <variable>`. The confirmation row and snapshot are written by a hook (`confirmRun`). `src/lib/verbs/data/run.mts:44-58`; `src/lib/shared/data/confirm.mts:39-85, 100-107`; `src/lib/shared/data/plan.mts:78-84`; `src/lib/shared/env/standard.mts:42-44`.
- **R-017** [VERIFIED] In this order the records sort by writer: the hook `route/verdict` and `inject/state`, `emit/statusline` write state from hooks; verbs `close`, `leave`, `mutate`, `preflight`, `summary`, `test`, `env init`, `uninstall`, `statusline` write files directly. The list comes from a grep for `appendJsonl|writeFileSync|renameSync`; verbs that write through shared helpers (`set`, `route`, `comment`, `waive`, `data approve`) are not in it and were not traced. `src/lib/hooks`, `src/lib/verbs`.
- **R-018** [VERIFIED] On Linux and WSL2 a `denyWrite` entry for a file that does not exist makes the sandbox create a 0-byte read-only placeholder while a sandboxed command runs and remove it afterwards; `allowWrite` for a missing path has no effect. `sandboxing`, "Filesystem rules", troubleshooting heading 14. Records such as `work/<id>/verdicts.jsonl` do not exist until first written.
- **R-019** [INFERRED] Kernel records share folders with files agents must write. `work/<id>/` holds both kernel files and agent artifacts (`order.md`, `research.md`, `reviews/`), and `.picket/state/` holds `scratch/` and `branching.yaml`. A directory-level deny would block those too; the settings list no wildcard syntax for `denyWrite`, so per-file or per-item entries may be needed. `src/lib/shared/kernel-records.mts:3-18`; `src/lib/shared/paths.mts:33`. [ARCHITECT REVIEW NEEDED]
- **R-020** [INFERRED] Even with every record path read-only, a determined agent that holds the connection string still reaches the database from its sandbox only if the network allows it: sandboxed database drivers ignore the proxy (R-009), so the direct route is blocked by default on Linux and WSL2 unless the client is HTTP. This is a different mechanism from R-005 and the docs do not say it is a guarantee. `sandboxing`, "Network".
- **R-021** [VERIFIED] `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials from subprocesses sandboxed or not, and the hooks page says a hook process inherits the parent environment except the variables that scrub removes; `credentials.envVars` deny affects sandboxed commands only. `sandboxing`, "Environment variables"; `hooks`, "Environment variables".

## Dependencies and relationships
The route rests on Claude Code settings (sandbox keys, managed scope for a lock, `allowUnsandboxedCommands`), bubblewrap and socat on Linux and WSL2, and the container engine (`engine.mts`, docker or podman), which the sandbox cannot host (R-009). SDR 00005 TF-003 is the decision this report feeds; D-002 to D-005 already route the SQL confirmation through a hook and a permission dialog.

## Risks and unknowns
- [UNKNOWN] Whether a teammate's Bash gets a different sandbox from the lead's, and how agent teams processes are sandboxed: the sub-agents excerpt says nothing, the agent teams page was not read.
- [UNKNOWN] Whether `denyWrite` accepts globs, and whether it blocks creating new files and renames inside a denied directory; the sandbox page excerpt gives no example.
- [UNKNOWN] The sandbox page's Security limitations section and the `sandbox` key defaults, which the fetch tool cut off.
- [UNKNOWN] How `picket drive` fares: its servers, ports and browser steps were not traced, so only the documented limits (Linux/WSL2 localhost is private, Chromium needs user namespaces, `allowNestedUserNamespaces` weakens protected paths) are known. `picket check` was not read at all.
- [UNKNOWN] Which verbs write records through shared helpers (`set`, `route`, `comment`, `waive`, `data approve`), so the set that would have to move into hooks is not complete.
- [UNKNOWN] Behaviour of a hook write that overlaps a running sandboxed command and its placeholder (R-018).
- [UNKNOWN] Whether the lead's `picket` calls could be excluded by exact text without opening the whole `picket` prefix to agents; the documentation on matching suggests only text, not caller.
- [ASSUMPTION] Documentation text is read as written; nothing was probed on this machine, so no claim about real behaviour under bubblewrap is verified.

## Recommendations
Describing only. What would have to move into hook processes if record writes may come only from outside the sandbox: every verb that appends to or replaces a kernel record (R-016, R-017), plus the `data run` confirmation take and run row, because the verb runs in the sandbox. What cannot be done at all: any isolation on native Windows (R-003); a different sandbox for the lead's and an agent's Bash, as far as the documents show (R-004); a hook that runs a container engine on the agent's behalf and returns the output is not described by the documents. Decisions for the architect: where the lead's verbs run (R-013) and how per-item record paths are denied (R-019). [ARCHITECT REVIEW NEEDED]

## Glossary
- **Excluded command**: a command matching `sandbox.excludedCommands`, run outside the sandbox with no filesystem or network limit.
- **Kernel record**: a file only the kernel or its hooks may write; listed by `KERNEL_OWNED_ENTRIES` and `isHookOnlyState`.
