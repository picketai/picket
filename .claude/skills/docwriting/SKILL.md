# Docwriting

The site is built by Zensical from `docs/` and published to https://picketai.github.io/picket/ on every push to trunk. The goal the user set: a site that describes Picket fully without being overbearing. The user decides what is shown; this skill decides how a page is formed.

## The reader

The reader is a developer, a person, not a model. Every page has to be easy to follow, and that is a balance the user set on 2026-11-22: too much on a page and it does not help, too little explanation and it does not help, the important thing not marked and it does not help, everything marked and it does not help either. Before a page is done, read it as that developer would: can they follow it top to bottom without a second page, and is the one thing they must not miss the one thing that stands out?

## Before you write

1. Name the reader's need in one sentence, then pick the page kind with the two questions in `diataxis.md`. A page has one kind.
2. Check every fact against the code or by running the command. A page states only what is true today; a feature that does not exist is said not to exist.
3. Read `zensical.md` for the page pattern and the features that render here.

## The four kinds, in one line each

| Kind | Reader | Form |
|---|---|---|
| Tutorial | studies by doing | one concrete goal, "we will", a visible result at every step, no choices |
| How-to guide | works by doing | titled "How to <goal>", steps only, no teaching |
| Reference | works, looks up | neutral description in the product's own structure, one pattern for every page |
| Explanation | studies by reading | titled as "About <topic>", answers a why, no steps |

A page that mixes kinds is split and the parts link to each other. That, and never cutting content, is what keeps the site light.

## Where things live

| Path | What it is |
|---|---|
| `zensical.toml` | site name, navigation, theme features, fonts, the dark palette |
| `docs/` | every published page; a page missing from `nav` is still published |
| `docs/reference/cli.md`, `docs/reference/hooks.md`, `docs/reference/mods.md` | generated by `npm run docs`; change `scripts/docs.mjs`, never the page |
| `docs/stylesheets/picketai.css` | generated by `npm run docs` from `src/themes/picketai.json` |
| `docs/stylesheets/layout.css` | hand-written layout rules; today it makes every table the full width of the text |
| `docs-theme/` | theme overrides: the wordmark in `docs-theme/partials/logo.html` and the social preview tags in `docs-theme/main.html` |
| `docs/images/` | the favicon and the social preview card, both cut from the logo |
| `design/` | the design system snapshots; outside `docs/` so they are not published |
| `.github/workflows/docs.yml` | builds with Zensical pinned to one version and deploys to Pages |

A change to `src/` or the workflow is a change to the product and goes through `picket admit`. A change to hand-written pages, navigation, this skill, or how `scripts/docs.mjs` prints a generated page is made directly in the main session, with its tests in `test/repo/docs.test.mjs` and a full `npm test` (the user ruled this on 2026-11-22).

## Writing a page

1. Start from the page skeleton in `zensical.md`: front matter with `icon`, the title, a lead of two sentences.
2. Keep one main path down the page. Prerequisites, options and limits go in admonitions; variants go in content tabs, and only when the variants differ.
3. Let the content choose the shape, and use the lightest one that fits: a command or an output in a code block, a sequence as a numbered list, values the reader compares in a table, variants in tabs. Plain sentences carry everything else. At most one box in a section, and only for content off the main path; a fact on the main path is never boxed. The user's two rulings of 2026-11-22: prose with no structure does not read clearly, and a page of boxes, small tables and tabs reads as cluttered.
4. A page that shows a flow stays minimal: the steps in order, one example, and links. The detail of each step (replies, options, limits, edge cases) lives on a page of its own, and is not repeated under the flow. The user ruled this on 2026-11-22 for "The daily loop".
5. Add the page to `nav` in `zensical.toml` under its tab. A new sidebar group is added only when it has pages to hold.
6. When content moves out of an older page, delete it there in the same change and link to the new page. One copy of every fact.
7. Follow the always-loaded writing rules: no dashes as punctuation, plain English, the user-facing name Picket and never "harness".

## Check and preview

Python's venv module is not installed on the maintainer's machine, so both commands use the container image. Run them from the repository root.

```sh
podman run --rm --userns=keep-id -v "$PWD":/docs:Z docker.io/zensical/zensical build --strict --clean
podman run --rm --name picket-docs-preview --userns=keep-id -p 127.0.0.1:8000:8000 -v "$PWD":/docs:Z docker.io/zensical/zensical serve -a 0.0.0.0:8000
```

The build must print `No issues found`; it writes the site folder at the repository root, which git ignores. The preview is at http://127.0.0.1:8000/picket/ and rebuilds on every save. After a change to a generated page's source, run `npm run docs` and `npm test`.

## Working method

Work one page at a time and leave the site complete after each: every published page useful as it stands, no empty section, no "coming soon". The top-level structure grows from the pages that exist; it is never laid out in advance. Commit and push only when the user asks; a push to trunk publishes.
