# Report: Lessons from three unread assets transcripts

## Summary
The three talks teach one loop from three sides: define the agent system in code, record every run, score runs, and let the records change the system [VERIFIED]. Picket already has the first two and part of the third: a read only versioned core, a kernel that computes the lane graph, a ledger row per turn, hooks that deny comments and silenced tests before the fact, and a close step that counts repeated review classes and writes an escaped defects note into agent memory (R-014) [VERIFIED]. The gaps are failed tool calls that the ledger does not record (R-031), no score trend, no measure for the prose rule or for redundant tests, and no path from a failed work item to a bench task [INFERRED]. Automatic edits to skills clash with a read only core and need a strategic call, with extensions as the bounded target the docs name (R-018) [INFERRED]. No talk gives a reason to stop a Picket practice, and the three are vendor pitches: Skill Doctor exists, the Neo4j paper was not found [VERIFIED].

## Context
Scope as understood: learn what the three talks teach, compare each practice with Picket's lanes, agents, kernel, hooks, skills, ledger and bench, and list what Picket does already, could do, or could stop doing; report only, no design or code. Out of scope: the 2026-11-14 transcript, and checking claims beyond reliable public sources.

## Findings
- **R-001** [VERIFIED] The software factory talk (Zach, founder and CEO of Warp) says most companies sit at interactive prompting and want automated development: a cloud loop where humans put work in and agents triage, spec, implement and verify with computer use. Local agents are bottlenecked by a person, hard to cost and hard to govern, and a compromised local agent holds the signed in user's rights. `assets/software-factory-transcript.md (1:12 to 3:55)`.
- **R-002** [VERIFIED] He asks that a factory be open (any model, any harness), adaptable, and defined in code under version control: workflows, skills, MCPs, where they run, agent definitions, benchmarks. The point is that versions of the factory can be tested and a coding agent can edit it. `assets/software-factory-transcript.md (4:02 to 5:14, 10:33 to 11:52)`.
- **R-003** [VERIFIED] He asks for measurement first on your own data: scorers (an LLM as judge) over every run, scores fed to agents that improve the factory, and a private benchmark built by replaying past agent tasks across models. His example chart: one model 93 percent correct for $2, another 95 percent at three times the cost. Correctness there is judged by an LLM; he admits human grading is missing. `assets/software-factory-transcript.md (6:01 to 6:46, 14:42 to 17:00, 20:44 to 21:17)`.
- **R-004** [VERIFIED] He splits engineering into product engineering (work put into the factory) and factory engineering (skills, context, model mix). In the Q and A he names two ways to cut review load: spec driven development and computer use evidence that the thing works from the user's side. Cost per PR is the budget measure he gives. `assets/software-factory-transcript.md (6:55 to 7:51, 18:06 to 19:30)`.
- **R-005** [VERIFIED] The self improving agents talk (Ben Holmes, Warp developer experience lead) describes one loop: collect every conversation with its tool calls and outputs, score each with a rubric, then a daily agent reads the failures and proposes changes to skills and config. Example scorers: redundant tests, verbosity (comments and summaries), efficiency over tool calls. Grading runs when a PR merges, with optional random sampling. `assets/yt-transcript-agentstest.md (2:41 to 3:13, 5:10 to 7:54, 10:42 to 13:31)`.
- **R-006** [VERIFIED] The speaker's main finding is silent waste: agents work around stale skill text (probing port numbers, missing sub agent config) and report success, so the only visible sign is a run two minutes longer than expected. Skill Doctor, a skill he links, grades past local sessions once; a continuous version tracks scores over time so a merged skill change can be tied to a score inflection. `assets/yt-transcript-agentstest.md (7:54 to 8:52, 13:46 to 18:55)`.
- **R-007** [VERIFIED] The graph engineering talk (a Neo4j speaker, name not in the transcript) defines graph engineering as designing agent work as an explicit graph, in three kinds: execution graphs (routers and agents as nodes), context graphs (decision traces and memory) and procedural graphs (a skill as steps). He says the mechanisms are old and the name is new. His benefits: predictability, governance and audit, and portability between runtimes. `assets/graph-engineering-transcript.md (0:36 to 3:52)`.
- **R-008** [VERIFIED] His central claim: compile a skill (SKILL.md, scripts, references) or a set of past successful runs into a deterministic graph in YAML, give the agent a CLI that runs it, and routing is no longer the model's job. Reported effects: higher task reward in a workshop paper, a loan approval demo whose wall clock fell from about 7.5 minutes to between 0.5 and 2, and a switch to a cheaper model. He calls the demo "not a formal research proposal"; the numbers are his own and unchecked here. `assets/graph-engineering-transcript.md (6:54 to 8:13, 14:28 to 19:53)`.
- **R-009** [VERIFIED] He adds observability on the graph: persist each run with its steps, then ask which branches were taken and which never were, which he calls useful for governance. Hard rules run first, a decision model gets what remains, a human review is a routed branch, and a lint loop checks the report. `assets/graph-engineering-transcript.md (15:42 to 18:34)`.

## Glossary
- **Software factory**: a loop where humans put work in and agents triage, spec, build and verify it, run as shared infrastructure.
- **Scorer**: a rubric an LLM judge applies to one agent run, giving pass or fail with a reason.
- **Graph shaped skill**: a skill written as steps and branches in YAML, run by a program, so the model does not choose the route.
- **Review class**: the checklist row id (`Ts4`) behind a Critical or Major finding; `picket close` reports a class named in two or more reviews.
