## Phase 2 of 20261105-kernel-blocks-run-sends-item-diffs: The phase commit always carries the work folder

Phase 2 is done and staged: phase and close commits now always include `work/<id>/`, even while another process holds `.git/index.lock`. A failed update of the shared index after the commit is now a warning, not an error.

`commitOwned` in `src/lib/shared/git.mts` no longer runs `git add` on the shared index. The commit is built in a temporary index in three steps: it starts from HEAD plus the owned staged paths, `git add -A` stages each `add` path there through `gitStrict`, and the commit's file list is that index's diff against HEAD. When the diff is empty, nothing is committed and `sha` is `null`. When the shared index cannot be updated after the commit (`syncSharedIndex`), the result gets the warning `index not updated after <sha>: <git error>; run git reset -q -- <paths>`, and the sha is still returned, so the ledger still gets its accept row.

Red: under a held index lock the commit still takes the work folder and warns that the shared index was not updated failed: git reset failed: Another git process seems to be running in this repository, or the lock file may be stale
Root cause: phase commits could miss `work/<id>/` because `commitOwned` staged the work folder in the shared index through `gitRead`, which drops a failed `git add` (such as a held `index.lock`), while the commit itself ran on a temporary index and succeeded.
