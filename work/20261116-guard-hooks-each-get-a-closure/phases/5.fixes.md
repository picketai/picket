## Phase 5 of 20261116-guard-hooks-each-get-a-closure: guard.comments gets a closure

I fixed the checkpoint's major finding. An HTML comment on the same line as a `<script>` or `<style>` element is a comment again, which restores the deny that `fdd3a2fa` gave. The comment can come before the opener, after the closer, or after a multi-line block's closer. The vocabulary now seeds those forms, so the closure keeps them closed.

After `npm run build` I fed Write events to `dist/hooks/guard.comments.mjs`. `<!-- note --><script>a()</script>` in `.html`, `<style>a{}</style><!-- note -->` in `.htm` and `</script><!-- note2 -->` in `.vue` were denied, and `<p>a</p><script>a()</script>` got no decision.

Decisions:
- A row with regions now reads a line part by part. In markup, the text before an opener is read with the markup row. Inside an element, the text before its closer is read with the region's language. The rest of the line is read again from the top. The opener search ignores text inside `<!-- -->`, so `<!-- <script> -->` opens no region. When a multi-line markup comment closes partway through a line, the rest of that line is read too (`x --><script>// y`). Rows without regions read lines exactly as before.
- Minor finding: I kept `export` on `realPath`. Phase 4's must_have grep `export function realPath\b` pins it, and `guard.scope` reads the same real path through `target.rel`, so importing `realPath` there would be an unused import.
