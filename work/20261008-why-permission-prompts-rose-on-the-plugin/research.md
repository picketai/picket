# Report: Why permission prompts rose on the plugin

## Summary
Prompts per task rose from 0.23 (rework-clean.json) to 3.57 (plugin-core.json), and from 1.0 to 7.0 on the two shared design-lane tasks [VERIFIED]. Claude Code's documented permission engine splits every Bash command on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines, and an allow rule must match each resulting subcommand independently; the plugin run's agent produces far more commands with at least one unmatched subcommand (an inline `API_KEY=` assignment, a `node core/bin/tether.mjs` fallback branch, a bare `grep`, a `>` redirect into the OS temp directory) than the rework run ever did [VERIFIED]. None of this is prescribed by the lane skill text, which only ever writes a single bare `tether <verb>` call; the compound forms are the benchmarked agent's own runtime improvisation, plausibly because nothing in this repo makes a bare `tether` command resolve on PATH [VERIFIED for the absence of any such mechanism; INFERRED that this is why the agent improvises]. Workspace trust and the PowerShell allow-rule gap are real but pre-existing conditions, present in both harnesses, and do not explain the rise. `tether init` does not exist yet, so the question's "what must it write" is a build decision, not a configuration tweak.

## Context
Asked: why permission prompts rose between the two bench result files for design tasks, grouped by tool and command, with the allow rules, plugin settings or hook changes that would remove each group, plus what `tether init` must write into a project's permissions. This deep pass read every source queued by the outline: the lane skill step files, `core/bin/tether.mjs` and the project's `package.json` (to check for a `tether init` verb and a PATH-resolution mechanism), `bench/run.mjs` and `bench/lib/trust.mjs` (to check how the bench's own `--allowedTools` flag and workspace trust interact with the repo's `.claude/settings.json`), the `.claude/settings.json` and commit `a380774` used by the rework run, and Claude Code's own permissions documentation. Not read: the live runtime trace of why `tether` fails to resolve on PATH in a bench-installed plugin repo (R-019 is inferred from the pattern of probes in the log, not confirmed by reproducing the failure).

## Structure
Two JSON result files (`manifest` + `records[]`); each record's `prompt_log` is one entry per call Claude Code made to `bench/lib/approver-mcp.mjs`, the `--permission-prompt-tool` invoked whenever a command is not resolved by the active deny/ask/allow rules. `bench/run.mjs` spawns `claude` with `cwd` already set to the installed repo (`bench/run.mjs:163-176`), trusts that workspace first (`bench/run.mjs:160`, `bench/lib/trust.mjs:26-33`), and passes `adapter.allowedTools` as the CLI `--allowedTools` flag (`bench/run.mjs:169`), which combines with the repo's own `.claude/settings.json` permissions as one allow-rule set (per Claude Code's documented settings precedence). The lane skills (`core/skills/{ordering,designing,researching}/steps/*.md`) are the only place the benchmarked agent's `tether` command text is specified.

## Findings
- **R-001** [VERIFIED] Prompts per task: rework-clean.json overall 0.23 (26 records), plugin-core.json overall 3.57 (14 records); design lane 1.0 to 7.0 on the two shared tasks (`gate-13-api-key-auth`, `gate-14-status-migration`); order lane 0 to 5.75; fast lane 0.22 to 1.67; research lane 0 to 1.5. Hook denials moved the other way, 0.19 to 0.07. `bench/results/rework-clean.json`, `bench/results/plugin-core.json`.
- **R-002** [VERIFIED] Every Bash prompt_log entry in plugin-core.json is a compound command: e.g. `(tether state <id> 2>&1 || node core/bin/tether.mjs state <id> 2>&1); ls; ls work; git ls-files | grep ...`, `cd D:/.../repo && API_KEY=test-key-123 tether drive --hit ...`, `mkdir -p "$TEMP/tether-scratch" && cat > "$TEMP/tether-scratch/request-api-key.md" <<'EOF'`. None is a bare single-command call. `bench/results/plugin-core.json`.
- **R-003** [VERIFIED] rework-clean.json's prompt_log has only 6 entries across 26 records: `cp data/config.json ...` (a `cp`/`||`/`;` chain), a multi-line `node ... & ... sleep ... kill ...` script, an intentional `AskUserQuestion`, a PowerShell `Remove-Item`, a bare `grep -n`, and a `for n in 1 2 3; do node .claude/bin/harness.mjs verify ...; done` loop. None names `tether`; rework drove `.claude/bin/harness.mjs` directly. `bench/results/rework-clean.json`; `bench/adapters/rework.mjs` (git show 48cac0c^).
- **R-004** [VERIFIED] `.claude/settings.json`'s `permissions.allow` has `Bash(tether *)` plus a short list of other single-verb Bash patterns (`node .claude/scripts/*`, `npm test*`, `npm run *`, `npx vitest*/tsc*/eslint*`, several `git ...*` read forms, `git add *`, `git commit *`, `git worktree list*`); no `PowerShell(...)` entry and no `permissions.additionalDirectories` entry exist; no entry covers `cd`, `cat`, `ls`, `mkdir`, `head`, `tail`, `echo`, `sed`, or `grep`. `.claude/settings.json:9-42`.
- **R-005** [VERIFIED] 3 plugin-run prompts are plain, unchained PowerShell calls (`tether admit --text "..."`, two `Get-Command tether` probes); they prompt purely because no `PowerShell(...)` allow rule exists anywhere. This gap is not new: rework-clean.json's own `Remove-Item` prompt (R-003) shows the same PowerShell gap existed before the plugin. `bench/results/plugin-core.json`, `bench/results/rework-clean.json`.
- **R-006** [VERIFIED] `bench/adapters/plugin.mjs`'s `install()` copies the harness root's `.claude/settings.json` verbatim (deleting a `hooks` key the file doesn't carry today, a no-op) and adds no `permissions.allow` entries for the installed repo (`bench/adapters/plugin.mjs:20-41`). Its `allowedTools` export, `[...trunk.allowedTools, "Bash(tether *)"]` (`bench/adapters/plugin.mjs:79`), is passed by `bench/run.mjs:169` as the CLI `--allowedTools` flag, which Claude Code combines with the repo's own settings as one allow-rule set, not a separate or overriding one (per Settings precedence in the permissions docs: "no other level, including command line arguments, can override" a higher-precedence rule, implying lower levels add rather than replace).
- **R-007** [VERIFIED] `guard.bash.mjs`'s `decide()` sets `hookSpecificOutput.permissionDecision` to only `"allow"` or `"deny"`, never `"ask"`; its one rule about compound tether commands denies a destructive sub-command "wrapped in a tether verb" and explicitly defers the non-destructive case to "the permission prompt" (`core/lib/hooks/guard.bash.mjs:148-154,792,796`). Per Claude Code's hooks documentation, a PreToolUse hook's `"allow"` is only overridden by an already-matching deny or ask rule; for a command with no matching rule at all (today's case for every group below), a hook `"allow"` would skip the prompt entirely. This is an available, currently unused lever, not a dead end.
- **R-008** [VERIFIED] code.claude.com/docs/en/permissions, "Compound commands": "Claude Code is aware of shell operators, so a rule like `Bash(safe-cmd *)` won't give it permission to run the command `safe-cmd && other-cmd`. The recognized command separators are `&&`, `||`, `;`, `|`, `|&`, `&`, and newlines. A rule must match each subcommand independently." This is the documented mechanism behind R-002; it supersedes the outline's inferred version of this finding.
- **R-009** [VERIFIED, corrected from the outline] The outline guessed that `cd <path> &&` prefixes and the `(tether X || node core/bin/tether.mjs X)` fallback were uniformly "compound commands breaking the match." The deep pass found three distinct, more precise causes, split out as R-010 to R-012 below; the outline's blanket explanation is not wrong in spirit but was imprecise about which part of each command actually fails to match, and is superseded by the specific findings.
- **R-010** [VERIFIED] code.claude.com/docs/en/permissions, "Read-only commands": "A `cd` into a path inside your working directory ... is also read-only, and a compound command like `cd packages/api && ls` runs without a prompt when each part qualifies on its own." Since `bench/run.mjs:163-164` spawns Claude with `cwd` already set to the installed repo, `cd D:/.../bench/.runs/<task>/repo && ...` targets that same directory and is a documented no-op. The `cd` prefix itself is not why these commands prompt.
- **R-011** [VERIFIED] The actual blocker in `cd <repo> && API_KEY=test-key-123 tether drive ...` (plugin-core.json, `gate-13-api-key-auth`) is the inline environment-variable assignment before `tether`. Per the docs' "Wrappers" section: "Claude Code also strips a leading assignment of certain known-safe environment variables, so `Bash(npm test *)` matches `NODE_ENV=test npm test`. An allow rule won't match past an assignment of any other variable." `API_KEY` is not a known-safe variable, so `Bash(tether *)` never matches this subcommand, chained or not.
- **R-012** [VERIFIED] The `(tether X 2>&1 || node core/bin/tether.mjs X 2>&1)` fallback (plugin-core.json, `gate-13`, `gate-14`) always contains one `||` branch, `node core/bin/tether.mjs X`, that cannot match any current allow rule: not `Bash(tether *)` (wrong leading word) and not `Bash(node bench/*)` or `Bash(node .claude/scripts/*)` (wrong path). Per the docs, "deny and ask rules apply when any subcommand matches them, including a command nested inside a subshell"; the allow check is symmetric, so every subcommand in either `||` branch must independently match. This idiom, as written, can never be fully allow-listed; it needs either a rule for the literal fallback path or removal of the need for the fallback (R-019).
- **R-013** [VERIFIED] Several compound commands also fail on a bare `grep` (`grep -n`, `grep -v`, `| grep ...`), in both plugin-core.json and rework-clean.json's own `grep -n` entry (R-003): Bash `grep` has no allow rule in `.claude/settings.json` or in either harness's `--allowedTools` (only the separate `Grep` tool is allow-listed, which is a different tool from a Bash `grep` invocation). This gap predates the plugin; it fires more often now only because plugin's commands chain `grep` onto `tether` calls far more often than rework's did.
- **R-014** [VERIFIED] `mkdir -p "$TEMP/tether-scratch" && cat > "$TEMP/tether-scratch/request-api-key.md" <<'EOF'` (plugin-core.json, `gate-13-api-key-auth`) does not fail on `mkdir` or `cat` verb coverage (both are in the bench CLI's `--allowedTools`). Per the docs' "Redirections" section, a `>` output-redirect target "covers your Edit allow and deny rules ... and the working directories," and `$TEMP` resolves outside the project's working directory, so the write needs approval regardless of `cat`'s own allow status. The heredoc body itself is explicitly exempt ("here-docs and here-strings" carry no file target to check), so the heredoc syntax is not the cause; only the temp-directory location is.
- **R-015** [VERIFIED] `.claude/settings.json` has no `permissions.additionalDirectories` entry (R-004). Per the docs, a directory listed there "follow[s] the same permission rules as the original working directory," so adding the OS temp directory (or retargeting the scratch file into the repo, R-018) would remove R-014's prompt without broadening any Bash allow rule.
- **R-016** [VERIFIED] Workspace trust is not a contributing factor to the regression. `bench/lib/trust.mjs:1-6` documents that an untrusted workspace makes Claude Code ignore a project's own `permissions.allow` entirely, and that this was true of "every bench run so far" before the trust fix landed; but within rework-clean.json, trusted and untrusted records show similar prompt rates (0.33 vs 0.22 average, n=3 trusted vs n=23 untrusted), and every plugin-core.json record is already trusted, so the two files are comparable on this axis and trust does not explain the rise.
- **R-017** [VERIFIED] The lane skill step files only ever write bare, single `tether <verb> ...` invocations (`core/skills/ordering/steps/10-order.md:6-7`, `20-phase.md:24`, `30-gate.md:8,32-35`; `core/skills/ordering/steps/40-review.md:6`; `core/skills/designing/steps/10-design.md:4-5`; `core/skills/researching/steps/10-outline.md:4`). None chains a second command, prefixes `cd`, or uses a `node core/bin/tether.mjs` / `npx tether` fallback. The compound forms in plugin-core.json's prompt_log are the benchmarked agent's own runtime improvisation, not instructions from the skill text.
- **R-018** [VERIFIED] `core/skills/ordering/steps/10-order.md:10` and `core/skills/designing/steps/10-design.md:8` both instruct: "A request with quotes or newlines goes in a scratchpad file passed as `--request <file>` instead," without naming where that file should live. The `gate-13-api-key-auth` agent followed this instruction but wrote to the OS temp directory, which is outside the working directory and triggers R-014's redirect-target prompt; naming an in-repo path (e.g. under `work/<id>/` or `.tether/`) would avoid it.
- **R-019** [VERIFIED that no mechanism exists; INFERRED that this causes the improvisation] `tether` has no path-resolution mechanism anywhere in this repo: the root `package.json` has no `"bin"` field (`package.json:2` names only the package `"aispec"`), and `bench/adapters/plugin.mjs`'s `install()` (R-006) places no `tether` executable or symlink on PATH. The lane skills assume a bare `tether` resolves (R-017); nothing in the installed repo makes that true. This plausibly drives the `Get-Command tether` probes and the `node core/bin/tether.mjs` / `npx tether` fallbacks (R-012), though the live runtime failure was not reproduced in this pass to confirm it directly.
- **R-020** [VERIFIED] `tether init` does not exist as a command today: `core/bin/tether.mjs:279` lists the complete verb set as `admit new list state set close next preflight verify route review-summary cost find-verdict drive check migrate comment packet pr source`, with no `init`. The question's premise, "what `tether init` must write into a project's permissions," is a build decision, not a change to an existing command. [ARCHITECT REVIEW NEEDED]

## Dependencies and relationships
Claude Code's own permission engine (outside this repo) performs the deny/ask/allow evaluation and subcommand splitting before `bench/lib/approver-mcp.mjs` (the scripted approver) or `core/lib/hooks/guard.bash.mjs` (the project's PreToolUse hook) ever see a call; both of those only run once a call has already been routed to a prompt or to the hook stage. `bench/lib/trust.mjs` controls whether the repo's own `.claude/settings.json` is consulted at all, independent of the CLI `--allowedTools` flag `bench/run.mjs` always passes.

## Risks and unknowns
- [UNKNOWN] The live runtime mechanism behind R-019's second half: whether `tether` actually fails to resolve (a "command not found") inside a bench-installed plugin repo, versus the agent probing defensively for an unrelated reason. Confirming this needs a reproduction run with verbose tool-call logging, not just the recorded prompt_log.
- [UNKNOWN] Whether a `node -e "..."` invocation's quoted script body is itself treated as a further subcommand by the splitter; one plugin-core.json entry (`fast-04-listen-error-log`) uses this form and was not traced against the docs' subcommand rules in this pass.
- [ASSUMPTION] Carried from the outline: read "design tasks 1.0 to 7.0" in the question as the overall per-task average (0.23 to 3.57) together with the two design-lane tasks found in the data (1.0 to 7.0); this is now cross-checked against the full per-lane breakdown in R-001 and is consistent with it.

## Recommendations
- [ARCHITECT REVIEW NEEDED] Build `tether init` and decide what it writes into a project's `.claude/settings.json`: at minimum a `PowerShell(tether *)` rule (R-005), a `permissions.additionalDirectories` entry for wherever the lane skills' "scratchpad file" convention resolves to when it is outside the repo (R-014, R-015, R-018), and either a way for `tether` to resolve on PATH after install or a fixed node-path invocation form the skills use instead of a bare `tether` (R-019), which would also remove the unfixable OR-fallback in R-012.
- [ARCHITECT REVIEW NEEDED] Decide whether `guard.bash.mjs` should also be extended to return an explicit PreToolUse `"allow"` for a compound command once every one of its subcommands is independently covered by an allow rule, since the docs confirm this is available and unused for commands with no matching rule today (R-007), as an addition to or instead of the installer/skill-side fixes above.
- Add a `Bash(grep *)` allow rule, or have the skills prefer the already-allow-listed `Grep` tool over a Bash `grep` call, to close the pre-existing gap in R-013; this is independent of the plugin-specific fixes and would also reduce rework-style prompts.
- Name an in-repo path (not the OS temp directory) in the "goes in a scratchpad file" instruction in `core/skills/ordering/steps/10-order.md:10` and `core/skills/designing/steps/10-design.md:8`, so the heredoc-based request-staging pattern stops writing outside the working directory (R-018).

## Glossary
- **approver-mcp**: `bench/lib/approver-mcp.mjs`, the bench's stand-in for a human reviewer; it is the `--permission-prompt-tool` Claude Code calls whenever a tool use isn't resolved by deny/ask/allow rules, and it auto-allows everything except a small destructive-command denylist, logging every call it sees as one "prompt."
- **subcommand splitting**: Claude Code's documented behaviour of breaking a Bash command on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines (including inside subshells and `for` loops) and requiring an allow rule to match each piece independently, rather than matching the whole command string as one unit.
- **workspace trust**: a per-directory flag in `~/.claude.json` (`hasTrustDialogAccepted`) that gates whether a project's own `.claude/settings.json` permission rules are consulted at all; an untrusted workspace falls back to only the CLI `--allowedTools` flag.
