Research, no code changes (SDR 00005 follow-up TF-003): can the host's Bash sandbox make the kernel's record paths read-only for agents' shells while Picket's hooks and the lead's picket verbs still write them? The records are the files under .picket/state/ that only the kernel writes (the data folder with approvals, confirmations and snapshots, the ledger) and the kernel-owned entries of work/<id>/ (state.yaml, verdicts.jsonl, comments.jsonl, waivers.jsonl, phases/). Answer for Claude Code on Linux, on WSL2 and on Windows: what the sandbox can restrict (paths, per tool, per subagent or only per session), whether hooks run inside or outside it, whether a spawned agent's Bash and the lead's Bash can get different rules, whether an environment variable such as PICKET_DATA_<SERVICE> can be kept out of an agent's shell, and what breaks for picket drive, picket check and the container engine under it. Say what would have to move into hook processes if record writes may come only from outside the sandbox, and what cannot be done at all. Sources: Claude Code's documentation and settings reference, and this repository's hooks and guards.

## Brief
purpose: Find out whether isolation by the operating system can stop a determined agent from writing Picket's records or reaching the database, which SDR 00005 names as the one route that would (TF-003).
in scope: Claude Code's Bash sandbox and permission settings on Linux, WSL2 and Windows: what paths it can make read-only, per tool, per subagent or per session; where hooks run; whether an environment variable can be kept from an agent's shell; what picket drive, picket check and the container engine need under it; what would have to move into hook processes
out of scope: Any code change; a design for the isolation; container or VM isolation outside Claude Code; other hosts than Claude Code
